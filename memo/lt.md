## 0. 一言でいうと

- **AIエージェント開発の知識（プロンプト・ツール選び・スキル・ガードレール・コスト）を、RPGのボスレイドとして競うゲーム**を、ほぼ口頭指示だけで作った。

## 2. 作ったもの

### コンセプト
- 参加者は「冒険者（AIエージェント）」を組む。ゲームの言葉と実務の言葉が対応している。

| ゲームの言葉 | 実務の言葉 |
| --- | --- |
| 心得 | システムプロンプト |
| 道具 | ツール |
| 巻物 | スキル |
| 結界 | ガードレール |
| 資料室 | ナレッジ／参照資料（ミスリード入り） |
| コスト上限 | トークン・費用の設計 |

- 役に立つ道具と、**役に立たない道具（ダミー）**が混ざっている。「選ぶ・削る・要約する」こと自体が腕の見せどころ。
- 例（初期シーズン「竜の巣」）: 資料を約300字に要約し、役に立つ道具だけ選ぶと満点。実APIで31/31を確認。
- 現行の練習シーズン: **吸血鬼伯爵討伐**。

### 体験の流れ
入る → 課題を読む → 組む → 試走（本番前に数問だけ試す）→ 提出 → 討伐（ドット絵のバトル再生）→ 戦果/ランキング → **診断**に従って直して再提出

### 工夫したところ
- **診断**: 点が低い理由をヒントで返す。実APIで、ヒントどおり直すと **33% → 56% → 82%** と上がることを確認済み。
- **ネタバレ防止**: 他人の正解の動き・心得・持ち物は画面に出さない。
- **非エンジニア向けUX**: コード不要、1日の提出回数制限、試走は提出回数を消費しない。
- **10言語対応**、翻訳の用語ずれを自動検査。
- 提出失敗（残高不足・APIエラー）時は回数を消費せず、理由を日本語で表示。
- OSの「視差効果を減らす」設定に応じて、光の演出を弱める。

### 公開方針（決定事項）
- 公開用リポジトリ（仕組み＋練習シーズンのみ）と、シーズン置き場（非公開）を分離。
- ライセンス: Elastic License 2.0（社内・個人・学校は無料、他者向けホスティングは商用ライセンス）。
- 静的デモをGitHub Pagesで公開。

## 3. 作り方

### 3-1. 依頼の仕方（口頭指示で足りる）
- 最初は「こういうゲームがほしい」程度のざっくりした日本語。設計・実装・テストまで任せた。
- 回し方のコツ（作業メモ・依頼書から）:
  1. **約束ごとを先に書く**（返答は日本語／費用は使う前に聞く／APIキーは画面に出さない）
  2. **「変えないもの」を明示**（ボスの体力係数、大技のダメージ、既存の演出など）→ 調整済みのバランスを壊されない
  3. **確認方法まで依頼に含める**（`npm test` が全部通る、全言語でチェックスクリプトOK、デモで討伐成功のまま、など）
  4. **1テーマ1コミット・全体は1PR**にまとめさせ、レビューしやすくする
  5. **UX設計案を先に文書化**してから実装に入る（コアループ、画面一覧、決めたいことを列挙）
- 決めるのは人間、実装と検証はClaude、という分担。判断が必要な点は「決めたいこと」として選択肢＋推奨付きで返してもらう。
- 運営の段取り（検証→試運転→告知→本番）も「あなたがやること」チェックリストとして文書化してもらった。

### 3-2. スマホから開発端末を外から動かす
- Mac mini上でClaudeデスクトップアプリを起動しておき、スマホのClaudeアプリから同じセッションに指示。
- 外出中・移動中でも「動作確認して」「直して」が投げられる。
- 【要確認・補足してください】実際の接続方法（どの画面から繋いだか）、通知の受け取り方、困った点。

### 3-3. クラウドセッションで別タスクを並行依頼
- 手元のセッションで本体開発を進めつつ、**公開準備の12項目**（翻訳検査、演出の軽減、再生の短縮、スマホ幅対応、E2E/CI、保存の堅牢化、OG画像、診断の実務対応、履歴、CONTRIBUTING等、描画のファイル分割、README動画撮り直し）を**別のクラウドセッション**に依頼書（Markdown）で渡した。
- 依頼書に「守ること」「確認方法」「PRの出し方」を書き、**成果はPRで受け取る**。マージ前に運営側セッションで確認。
- ポイント: 依存関係の薄いタスクを並列に投げられる。人間は待たずに別の判断（ホスティング、日程、予算）に回れる。

## 4. Kiroとの違い（LTでの主張案）

> 【要確認】Kiroは私の知識の範囲でのまとめ。最新機能は発表前に確認を。

| 観点 | Kiro | 今回のClaude運用 |
| --- | --- | --- |
| 開発の進め方 | 仕様駆動（要件→設計→タスク）をIDE上で構造化して進める | 口頭（チャット）の指示だけで進める。必要なら設計案はClaudeに文書化させる |
| 仕様の置き場 | 仕様ファイルが中心 | プロジェクトのドキュメントとメモ（作業メモ、依頼書、決定事項） |
| 動作確認 | IDE内・ローカル中心 | 画面キャプチャや動画を撮って、見た目の崩れを自動で見つけて自動修正 |
| 共有・確認 | リポジトリ／ローカルで確認 | **アーティファクト**で動くデモ・ドキュメントをその場でURL共有 |
| 操作場所 | IDE | デスクトップアプリ＋スマホ＋クラウドセッション |

### 主張のポイント（あなたの実感ベース）
1. **モデルの進化で、口頭指示だけで必要十分になりつつある。** 仕様書を先に厳密に作らなくても、対話しながら詰められる。
2. **目で見て直せる。** スクショ・動画（READMEの動画もスクリプトで撮影）を撮って、崩れを自動修正。スマホ幅375pxの確認もスクショ付きPRで依頼できる。
3. **アーティファクトで動作確認が軽い。** ビルド・デプロイ不要で、動くデモと募集要項ドキュメントをURLで共有（実際に、募集要項・デモをアーティファクト化している）。
4. 逆に**仕様駆動が向く場面**もある（大人数開発、仕様の合意が重要な案件）。対立ではなく使い分け、と添えると角が立たない。
